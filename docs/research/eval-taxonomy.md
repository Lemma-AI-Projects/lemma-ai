# Eval Taxonomy：技术调研报告的评估分类体系 V0

> 2026-10-26 · 为 Lemma AI 的技术调研报告（首例：Focus Mode 报告）建立的可复用评估体系。
> 设计原则：每个指标必须**可判定**（有证据来源），不允许"整体感觉好"式的评价。
> 评分 0–5；加权后给出总分；**任何 ≤2 的指标自动成为"必须修复项"**，不允许用其他
> 维度的高分稀释。

## 六个评估域

### S · Scope & Alignment（范围与对齐）— 权重 20%

| # | 指标 | 判定方式 |
|---|---|---|
| S1 | 任务覆盖度：brief 列出的任务逐条对照，缺一项即扣 | 对照 brief 任务清单打勾 |
| S2 | 决策对齐：已批准决策是否被忠实引用，无擅自扩展或降级 | 逐条对照决策来源 |
| S3 | 边界纪律：brief 的"明确禁止"清单逐条核查 | 对照禁止清单 |

### E · Evidence & Rigor（证据与严谨）— 权重 25%

| # | 指标 | 判定方式 |
|---|---|---|
| E1 | 主张分级贯穿性：[EF]/[EJ]/[DH]/[ORQ] 是否在**正文主张处**持续标注（不是只在开头宣称） | 抽样 10 处关键主张查标注 |
| E2 | 引用质量：原始论文/官方文档优先；博客与产品页必须可识别；不编造 | 逐条核来源类型 |
| E3 | 仓库事实一致性：引用的文件/行号/状态与代码一致 | 抽样 5 处对代码 |
| E4 | 冲突处理：资料矛盾被记录（来源+时间），而非静默取一 | 查冲突记录节 |

### T · Technical Depth（技术深度）— 权重 20%

| # | 指标 | 判定方式 |
|---|---|---|
| T1 | 机制具体性：给出可实现/可验证的机制（接口、字段、协议），不是概念罗列 | 抽样 3 处技术主张 |
| T2 | 选型验证：技术对比以官方文档/实测为据，不依赖二手评测 | 查选型章节引用类型 |
| T3 | 风险结构化：最高风险被识别且有实验对应 | 查风险→实验映射 |

### X · Experience & Interaction（交互与用户视角）— 权重 15%

| # | 指标 | 判定方式 |
|---|---|---|
| X1 | 场景完整性：brief 指定的完整场景（含逐要素）真实存在，不是被映射表替代 | 对照 brief 场景要求 |
| X2 | 干预/交互模型可操作：模型映射到具体 UI 机制与参数 | 抽样 3 处映射 |
| X3 | 失败条件：关键设计有"什么时候不工作"的记录 | 抽样 3 处 |

### A · Actionability（可执行性）— 权重 10%

| # | 指标 | 判定方式 |
|---|---|---|
| A1 | 实验可执行：RQ/H/Setup/成功/失败/Informs 齐全，且 Setup 真的能搭 | 逐条过 |
| A2 | Roadmap 依赖清晰：进入条件与决策节点明确，无时间/资源伪造 | 逐条过 |
| A3 | 决策节点：报告指出的"要拍的"有明确去向 | 查拍板清单 |

### D · Document Quality（文档与交付质量）— 权重 10%

| # | 指标 | 判定方式 |
|---|---|---|
| D1 | 结构与导航：章节按研究逻辑组织，索引可发现 | 通读 |
| D2 | 可视化：架构图/时序图/对比图**有信息价值地存在**（brief 要求则必须有） | 数图 + 查信息密度 |
| D3 | PDF 排版：每页 logo/中文字体/表格/分页/公式，逐项机器验证 | pypdf + 抽样截图 |
| D4 | 密度平衡：无 AI 味的水分，也无关键处缺句 | 抽样 3 段 |

## 评分汇总模板

| 域 | 得分 | 权重 | 加权 |
|---|---|---|---|
| S | /5 | 20% | |
| E | /5 | 25% | |
| T | /5 | 20% | |
| X | /5 | 15% | |
| A | /5 | 10% | |
| D | /5 | 10% | |
| **总分** | | | /5 |

**规则**：
1. 任何指标 ≤2 → 该报告**不可作为决策依据**，先修复；
2. 修复项修复后**只重评该指标**，总分重算；
3. 本 taxonomy 本身也是被评对象：用起来发现判不了、或两个指标总在打架，就修
   taxonomy（版本化）。

## 首例应用 · 自评《Focus Mode 交互机制与技术实现路线调研报告》（2026-10-26）

> 自评人 = 报告作者本人（同一 Agent），存在**自评偏差**——判定方式尽量用可机器核查
> 的证据（计数、对照 brief 逐条），主观项从严。

### 评分

| 域 | 得分 | 最重的扣分证据 |
|---|---|---|
| S | **4.7** | S1=4：brief Task 6（自述"重点验收任务"）要求**三个完整场景×10 要素**，报告正文只有映射表与散提及，**没有成章的场景** |
| E | **3.8** | E1=3.5：分级标注在理论章密集，§7–§11 关键主张处基本失标；E2=3.5：16 条引用中约 6 条是厂商博客/内容农场（Zooz/Zylos/techbloat 类），AIRIS 与 Keyhole 均为 **arXiv 预印本（未经同行评议）**却未显著标注 |
| T | **4.0** | T2=3：编辑器对比两处引用来自 SEO 内容农场文章；tldraw/ProseMirror 用了官方文档但**未实测 API**（"Chat starter kit 验证 Mala 形态"系转述） |
| X | **3.4** | X1=2（同 S1）；X2=4.5；X3=4 |
| A | **4.3** | E3 走查"2–3 人"规模太小，统计效力近零——已如实写 |
| D | **3.5** | **D2=1：全篇零图**——brief Part III §4 明确要求架构图/时序图/状态图，一张都没有，只有表格 |

**加权总分：3.98 / 5**

### 按规则一的判定

D2（=1）与 X1（=2）触发红线：**本报告当前不可作为最终架构决策依据**，须先修复。
可以作为**讨论稿与实验排期依据**（E1–E4 的设计不受影响）。

### 修复清单（按影响排序）

| # | 修复 | 工作量 |
|---|---|---|
| 1 | **补三个完整场景**（Laptop/Research · Tablet/Math · Agent-initiative，各 10 要素 + 技术映射），成章插入 §5 与 §6 之间 | ~150 行 |
| 2 | **补图 ≥4**：L1–L4 → UI 机制映射图 · 三路径架构对比图 · 三段式锚定示意 · Path B 交互时序 | 每图一小时内 |
